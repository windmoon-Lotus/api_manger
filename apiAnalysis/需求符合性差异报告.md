# API 自动化设计需求符合性差异报告

> 历史说明：本报告反映早期代码状态，其中 OpenAPI/Postman、AI、参数位置、
> 越权和管理能力等判断已过期。当前需求和验收基线以仓库根目录
> `REQUIREMENTS_V2.md` 为准；本文件仅保留为演进记录。

范围与依据
- 需求来源: `apiAnalysis/api自动化设计相关.docx`
- 代码来源: `apiAnalysis/` 目录下现有实现

结论概览
- 已实现: HAR/MITM 流量解析入库与基础参数扁平化。
- 部分实现: 参数归档与请求组合思路存在雏形, 但未形成可用闭环。
- 未实现或偏差较大: AI 辅助、OpenAPI/Postman 导入、参数位置与关系建模、接口分类治理、漏洞规则框架、版本/漏洞管理、用例自动生成等核心目标。

需求对照与差异明细

1) AI 辅助识别接口作用与异常判断
- 需求: AI 调用脚本与存储数据发起请求并判断异常, 可用 API 文档辅助识别。
- 现状: 未看到任何 AI 相关接口或调用逻辑。`apiAnalysis/rule/analysis.py` 仅基于关键字做简化判断, 且未接入主流程。
- 差异: AI 辅助能力缺失, 自动识别与异常判断未实现。

2) 多来源数据导入 (HAR/MITM/OpenAPI/Postman)
- 需求: 支持 HAR/中间人流量导入, 以及完整 OpenAPI/Postman 文档导入。
- 现状: HAR/MITM 导入已实现 `apiAnalysis/input/har_capture_reader.py`, `apiAnalysis/input/mitmproxy_capture_reader.py` 并在 `apiAnalysis/db/save.py` 里写入 `raw_data`。
- 缺失: OpenAPI 导入未实现, `apiAnalysis/input/openapi_reader.py` 为空, 仅有思路文件 `apiAnalysis/parsename_原始思路.py` 未接入主流程。Postman 导入未实现。

3) API 功能分类与可扩展规则体系
- 需求: 按增删改查/上传下载/鉴权等分类, 规则可扩展, 支持人工标注修正。
- 现状: `apiAnalysis/rule/analysis.py` 有基于路径/方法关键字的分类函数, 但未发现被主流程调用, 也未将结果落库到 `raw_data.action`。
- 差异: 分类规则未落地, 执行链路缺失, 人工标注入口不存在。

4) 参数位置与关系建模 (ReqP/ResP)
- 需求: 记录参数位置 (body/query/header/path) 与关系 (primary/secondary/any), 并形成参数化请求/响应体。
- 现状: `apiAnalysis/db/collection.py` 中 `req_data`/`res_data` 仅存参数名与值, 未记录位置与关系, 也未保存参数化体。
- 差异: ReqP/ResP 的核心字段缺失, 无法满足需求中的参数位置与关系分析。

5) 参数分析规则与弱相关推断
- 需求: 依据参数值交集推断请求/响应路径弱相关, 包含公式化规则与校验逻辑。
- 现状: `apiAnalysis/db/save.py` 只做参数扁平化与聚合, `apiAnalysis/rule/analysis.py` 中 `parameter_archive` 有局部验证尝试, 但未实现需求中描述的规则链与 swap 校验逻辑。
- 差异: 规则验证逻辑不完整, 需求中的核心推断规则未实现。

6) 请求组合表与自动组包
- 需求: 有请求组合表, 支持从参数组合生成请求包。
- 现状: `apiAnalysis/db/collection.py` 有 `generate_req` 基础结构, `apiAnalysis/tool/compose_request.py` 为临时方案且未接入主流程。
- 差异: 请求组合与自动组包未形成可执行闭环, 字段模型也与需求不一致。

7) 数据表结构字段差异
- 路径表: 需求字段含 `pathid`/`action`/`rule`/`des`/`tags`/`headers`/`modificator` 等。
  - 现状: `raw_data` 字段包含 `ptah_id` 拼写错误, `action` 未赋值, `headers` 与 `query` 存在, 但缺少需求中的 `heades`/`modificator` 等明确用途定义。
- 请求参数表: 需求字段含 `Priority`/`required`/`type`/`des`/`modificator`/`Path`。
  - 现状: `req_data` 缺少 `modificator` 与 `Path`, `Priority` 未使用。
- 响应参数表: 需求字段含 `modificator`/`Path`。
  - 现状: `res_data` 缺少 `modificator` 与 `Path`。
- 参数分析结果表: 需求为统一 `value` 字段。
  - 现状: `parameter_data` 分为 `req_value`/`res_value`, 语义与需求描述不一致。

8) 账号维度与同角色约束
- 需求: 分析前提为同角色权限下, 参数值需按账号维度管理。
- 现状: `PacketRecord` 有 `username`, 但 `parameter_data` 与 `raw_data` 聚合未区分账号。
- 差异: 无法保证同角色数据约束, 需求中的账号维度缺失。

9) 漏洞规则框架与越权/业务逻辑漏洞
- 需求: 集成漏扫规则框架, 增加越权等逻辑漏洞规则。
- 现状: `apiAnalysis/rule/insertauth.py` 仅为示例脚本, 未接入系统与数据流。
- 差异: 漏洞规则框架未集成, 越权检测未形成可用功能。

10) API 版本与漏洞管理
- 需求: 具备 API 版本和漏洞管理。
- 现状: 未发现版本或漏洞管理相关数据结构与接口。
- 差异: 功能缺失。

11) 功能测试用例自动生成
- 需求: 添加功能测试用例自动生成规则。
- 现状: 未见用例生成相关模块或规则引擎。
- 差异: 功能缺失。

12) 前端展示与人工修正
- 需求: 前端展示并允许修改接口属性, 纠正归类错误。
- 现状: `apiAnalysis/web/showtable.py` 只提供 `parameter_data` 的基础编辑页面, 未提供 API 路径/分类的管理界面。
- 差异: 缺少接口属性管理与分类修正能力。

已实现或接近实现的需求点 (供核对)
- HAR/mitmproxy 流量解析并入库: `apiAnalysis/input/har_capture_reader.py`, `apiAnalysis/input/mitmproxy_capture_reader.py`, `apiAnalysis/db/save.py`
- 请求/响应参数扁平化与聚合: `apiAnalysis/tool/tool.py`, `apiAnalysis/db/save.py`

风险与影响
- 没有 AI/文档导入能力将限制接口语义理解, 自动分析效果偏弱。
- 参数位置/关系缺失导致规则推断不可复现, 误报/漏报风险高。
- 缺少账号维度与权限前提, 易引入跨角色数据污染, 影响越权规则可靠性。

建议的优先修复方向
1) 完成 OpenAPI/Postman 导入并与 `raw_data`/`req_data`/`res_data` 建模对齐。
2) 补齐 ReqP/ResP 位置与关系字段, 并将其写入数据库。
3) 将接口分类与规则执行接入主流程, 支持人工修正入口。
4) 落实参数弱相关推断与校验逻辑, 形成可重复执行的规则链。
