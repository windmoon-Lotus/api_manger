# 认证工作台页面设计

## 1. 页面目标

认证工作台只解决四个用户问题：

1. 当前认证为什么不可用。
2. 系统已经从项目、环境、账号和现有 Recipe 中知道了什么。
3. 还缺哪些输入，修改会形成什么候选版本。
4. 验证会访问哪些认证地址、最多发送多少请求，成功后会产生什么认证上下文。

页面不再把某个产品协议做成顶层表单。蒲公英、普通账号密码、OAuth 或其他
SSO 都只是同一种 `Auth Recipe` 的不同版本。

## 2. 用户任务流

```text
进入认证工作台
-> 阅读机器诊断和缺失项
-> 选择快捷配置或工作流编辑
-> 本地预检 Recipe、认证 Origin、共享秘密引用和输出
-> 保存候选（零请求）
-> 用户显式验证候选（认证请求）
-> 成功后激活；失败时保留当前生效版本
```

保存和验证必须分开。用户可以先检查候选版本，只有“验证候选”按钮会发送认证
请求。验证按钮必须显示最大请求数，且页面要持续说明不会调用业务接口。

## 3. 信息架构

页面分为三个一级视图。

### 3.1 概览

- 项目、环境、测试账号和允许的业务 Host。
- 当前生效 Recipe 的人类可读摘要。
- 最近健康状态、失败阶段和建议动作。
- 必需共享秘密、已配置键名和缺失键名。
- “配置候选方案”和“查看版本记录”入口。

概览不显示 URL 输入框、JSON 或秘密值。

### 3.2 配置候选

提供三个逐级展开的编辑层级：

1. **快捷配置**：单次账号密码登录并提取 Token/Cookie。
2. **工作流编辑**：通用的变量转换和 HTTP 步骤编辑器。
3. **原始 Recipe**：专家直接编辑受限声明式 JSON。

工作流编辑器支持当前运行时已经具备的能力：

- `set`：literal、unix_time、uuid4、concat、md5、sha256、base64、rsa_encrypt；
- `http`：GET/POST、Header、Query、JSON/Form、成功状态、跳转、字段提取；
- `mfa_receive`：从允许的接收服务主动拉取，或通过受 Bearer 保护的短期事务接收
  工具推送；
- `output`：Bearer/Header、Cookie、Session Cookie 和过期时间。

Realm 共享秘密单独配置，Recipe 只引用 `{{secret.key}}`。页面只回显键名，不
回显值。填写新秘密默认与当前版本合并；完整替换必须显式勾选。

### 3.3 版本记录

- 候选状态、创建原因、步骤数和认证 Origin。
- 最近验证阶段、请求数和结构化错误。
- 草稿或失败候选可以显式重新验证。
- 已激活版本只读展示。

## 4. 页面布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 认证工作台    项目 / 环境 / 方案                   当前状态 │
├──────────────────────────────────────────────────────────────┤
│ 项目环境 │ 测试账号 │ 业务 Host │ 当前 Recipe                │
├──────────┬───────────────────────────────────────────────────┤
│ 概览     │ 机器诊断 / 缺失项 / 当前流程 / 下一步             │
│ 配置候选 │                                                   │
│ 版本记录 │                                                   │
│          │                                                   │
│ 安全边界 │                                                   │
└──────────┴───────────────────────────────────────────────────┘
```

视觉层级遵循：

- 结论先于配置；
- 人类名称先于版本 ID；
- 缺失项和失败阶段使用红色；
- 可验证但未验证使用橙色；
- 已验证并激活使用绿色；
- 原始 JSON、版本 ID、Origin 明细放在可折叠技术详情中。

## 5. 状态设计

| 状态 | 页面主结论 | 主要动作 |
| --- | --- | --- |
| `healthy` | 当前方案可用 | 查看流程、按需创建新候选 |
| `unknown` | 尚未验证 | 检查候选并验证 |
| `failed` | 指定阶段失败 | 按建议修复并保存候选 |
| `interactive_required` | 需要人工登录/MFA | 进入交互式适配器流程 |
| 候选 `draft` | 已保存，未发送请求 | 验证候选 |
| 候选 `failed` | 验证失败，当前版本未变化 | 编辑生成新候选或重试 |
| 候选 `activated` | 已验证并生效 | 只读查看 |

## 6. 安全和执行反馈

- 保存候选不发送网络请求。
- 验证只访问候选 Realm 的认证 Origin。
- 验证按钮显示 HTTP 步骤数和最大请求数。
- 验证尝试展示逐步时间线：准备、请求、响应、提取、输出。
- 不显示账号密码、Token、Cookie 或 Realm 共享秘密值。
- 候选验证失败不切换当前版本。
- 恢复暂停批次前仍使用既有的零业务进度检查。

## 7. 本轮验收标准

1. 页面上不存在蒲公英专属顶层配置区。
2. 普通用户默认只看到诊断、上下文、缺失项和下一步。
3. 多步认证可通过通用工作流编辑器表达。
4. 原始 Recipe 仍可编辑，但不是默认入口。
5. 保存候选与验证候选是两个明确动作。
6. 保存候选的自动化测试证明没有调用认证执行器。
7. 候选验证仍复用现有不可变版本、失败隔离和成功激活机制。
8. 页面在常见桌面宽度和窄屏下均不产生横向宽表。

## 8. 后续能力边界

AI 代码适配器和浏览器交互式适配器仍不在本轮伪装为可用功能。RSA 本地转换和
受限的 pull/push 二验接收器已经可用；其他交互步骤应继续使用
同一页面信息架构，但需要独立的受限运行环境、输入输出 Manifest、版本哈希和
验证记录后才能启用。
